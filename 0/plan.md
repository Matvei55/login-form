## 1. Результаты аудита кодовой базы (Текущие проблемы)

Перед внедрением новых фич необходимо устранить критические баги и архитектурные несоответствия, которые сейчас присутствуют в коде:

### А. Критические ошибки (сломают запуск или логику автозагрузки)
1. **Отсутствие зависимости `phpdotenv` и файла `.env`** `[Частично обойдено]`:
   * **Что сделано**: Студент добавил проверку `if (!file_exists($path)) { return; }` в `Config::load()`. Теперь приложение не падает, если файла `.env` нет (используются дефолтные значения).
   * **Проблема**: В `composer.json` по-прежнему нет зависимости `vlucas/phpdotenv`. Если создать файл `.env` в корне, автозагрузчик не найдет класс `Dotenv\Dotenv` и приложение упадет.
   * **Решение**: Выполнить `composer require vlucas/phpdotenv` и создать реальный файл `.env` для гибкой настройки БД.
2. **Баг авторегистрации в контейнере (`App/Container/Container.php`)** `[ИСПРАВЛЕНО]`:
   * **Исправлено в коммите c0dad41**: Скобка цикла `foreach` в `registerDirectory()` перенесена. Теперь при сканировании директорий в контейнере корректно регистрируются все класс-файлы.

### Б. Архитектурные несоответствия (Service Locator вместо DI)
1. **Контроллеры принимают конкретные зависимости** `[ИСПРАВЛЕНО]`:
   * `LoginController`, `PostsController` и `RegisterController` теперь используют Constructor Injection: принимают `Request`, `View`, `Session` и модели в конструкторах. Базовый `Controller` также рефакторирован.
2. **Перенос middleware на контейнер** `[ИСПРАВЛЕНО]`:
   * В `MiddlewareDispatcher` посредники теперь разрешаются из контейнера через `$this->container->get($middlewareClass)`. Это позволило избавиться от оператора `new`.
3. **Использование Service Locator в Middleware** `[ИСПРАВЛЕНО]`:
   * **Исправлено в коммите c0dad41**: В `AuthMiddleware`, `GuestMiddleware` и `LoggerMiddleware` добавлен конструктор `__construct(private Session $session)`. Контейнер автоматически внедряет экземпляр `Session` при их создании.
4. **Использование оператора `new` вместо разрешения через DI-контейнер** `[ИСПРАВЛЕНО]`:
   * **Исправлено в коммите c0dad41**: 
     * В `EventDispatcher` слушатели разрешаются через `$this->container->get($listenerClass)`.
     * В `AbstractModel` свойство `QueryBuilder` внедряется через конструктор (`__construct(protected QueryBuilder $builder)`). Модели `Posts`, `Tags`, `Users` передают зависимость в родительский конструктор.

### В. Хардкод параметров и связей
1. **Зашитые пути**: В `View.php` дефолтный путь шаблонов `/var/www/html/templates` прописан жестко в объявлении конструктора `__construct(private string $templatePath = '/var/www/html/templates')`.
2. **Динамические Middleware** `[ИСПРАВЛЕНО]`:
   * Логика назначения Middleware перенесена из `Router.php` в контроллеры с помощью свойств и метода `getMiddlewareConfig()`. В роутере настроено динамическое чтение правил из контроллера и слияние с глобальным `LoggerMiddleware`.

### Г. Новые замечания (по результатам последних коммитов)
1. **Критическое несовпадение типов событий и слушателей в `EventDispatcher`** `[ОШИБКА]`:
   * **Проблема**: В `Application::registerEvents()` слушатели по-прежнему регистрируются на старые классы событий:
     ```php
     $this->dispatcher->addListener(PostCreatedEvent::class, LogPostCreatedListener::class);
     $this->dispatcher->addListener(UserRegisteredEvent::class, LogUserRegisteredListener::class);
     ```
     Однако в `AbstractModel::save()` отправляются общие события `ModelSavingEvent` и `ModelSavedEvent`. При этом методы `handle()` в `LogPostCreatedListener` и `LogUserRegisteredListener` ожидают именно `ModelSavedEvent`:
     ```php
     if (!$event instanceof ModelSavedEvent) { return; }
     ```
     Поскольку `ModelSavedEvent` нигде не зарегистрирован в `Application.php` для вызова этих слушателей, события создания постов и пользователей отправляются диспетчеру, но **игнорируются**, так как для `ModelSavedEvent` нет слушателей. Логирование создания сущностей сломано.
   * **Решение**: Зарегистрировать слушатели на `ModelSavedEvent` в `Application::registerEvents()` или вернуть точечную отправку `PostCreatedEvent` и `UserRegisteredEvent` из дочерних моделей.
2. **Использование Service Locator в методах моделей (`Users.php`, `Posts.php`)** `[ЗАМЕЧАНИЕ]`:
   * В `Tags::getTagsForPost()` студент исправил замечание, заменив контейнер на `new Tags(...)`.
   * Однако в `Users::getFollowers()`, `Posts::getUser()` и `Posts::getPostsByUserId()` по-прежнему используется обращение к глобальному синглтону:
     ```php
     $container = Application::getInstance()->getContainer();
     $user = $container->get(Users::class);
     ```
   * **Решение**: Избавиться от Service Locator, передавая зависимости/фабрики или используя ключевое слово `new` (для моделей без сложного графа зависимостей).
3. **Некорректное получение session_id в `LoggerMiddleware.php`** `[ИСПРАВЛЕНО]`:
   * В коде `LoggerMiddleware.php` вызов вызова поправлен на `session_id() ?: 'none'`.
4. **Лишние неиспользуемые импорты (Dead Code)** `[ИСПРАВЛЕНО]`:
   * Импорты `use App\Models\Tags;` удалены из `AuthMiddleware` и `GuestMiddleware`.

## 2. Обзор целевой архитектуры фреймворка
Проект расширяется до структуры с разделением на Web-слой и CLI-слой:

```
[Клиент (Браузер)]
       │
       ▼
[pub/index.php (HTTP-вход)] ──► [Application] (Контейнер)
                                      │
                                      ▼
                               [Post/CommentService]
                                      ▲
                                      │
[bin/telegram-poll.php (CLI)] ────────┘ (Инициализирует Application,
       │                                 запускает бесконечный цикл)
       ▼
[Telegram Bot API] (Запросы getUpdates / Long Polling)
```

### Дополнительные концепции для обучения:
1. **Применение рекурсии (Recursion)**:
   * **В DI-контейнере**: Контейнер использует рекурсию в `resolveClass()`. Если класс `A` требует `B`, а `B` требует `C`, контейнер совершает рекурсивные вызовы для сборки дерева зависимостей.
   * **В комментариях (Дерево комментариев)**: Хранение вложенных комментариев в одной таблице с помощью ссылки на родителя (`parent_id`). Рендеринг древовидной структуры комментариев с неограниченной вложенностью в шаблоне будет реализован через рекурсивный вызов функции отображения.
2. **Двустороннее API через Long Polling (Консольный демон)**:
   * Реализация интерактивной модерации без публичного домена (без Webhooks). Пост/комментарий создается со статусом `pending` и отправляется в Telegram с Inline-кнопками. 
   * Консольный скрипт `bin/telegram-poll.php` запускается из-под Docker, инициализирует ядро фреймворка с контейнером и в бесконечном цикле опрашивает Telegram API (`getUpdates`). При получении нажатий кнопок он обновляет статус в БД через наши сервисы и редактирует сообщение в Telegram.
